# MorsePad — структура проекта и принцип работы кодировки

## 1. Модули

Проект состоит из двух Gradle-модулей. Граница между ними проходит по зависимости от Android:
вся логика ввода живёт в модуле, который физически не может импортировать Android API.

```
m-app/
├── core/   — чистый Kotlin/JVM: движок ввода, кодек, редактор, домен заметок
└── app/    — Android: Compose UI, Room, жизненный цикл, диагностика задержек
```

| Компонент из ТЗ (п. 3, 9) | Где реализован | Ответственность |
|---|---|---|
| **InputEngine** | `core/.../input/InputEngine.kt` | Сбор аккорда из независимых касаний, фиксация, отмена |
| **ChordCodec** | `core/.../codec/ChordCodec.kt`, `ChordSequenceDecoder.kt` | Маска ↔ символ; префикс `11111` |
| Таблица кодировки | `core/.../codec/ChordTableV1.kt` (данные), `ChordTable.kt` (валидация, реестр версий) | Хранится отдельно от логики декодирования |
| **TextEditor** | `core/.../editor/TextEditor.kt` | Единственное место изменения текста; авторегистр; удаление; отмена |
| Связка ввода | `core/.../session/TypingSession.kt` | Аккорд/спецклавиша → декодер → редактор; правила префикса |
| **NoteRepository** | интерфейс `core/.../notes/Note.kt`, реализация `app/.../data/RoomNoteRepository.kt` | Доступ к заметкам |
| Автосохранение | `core/.../notes/NoteAutosaver.kt` | Дебаунс, сериализация записей, ленивое создание заметки |
| **SettingsRepository** | интерфейс `core/.../settings/AppSettings.kt`, реализация `app/.../data/RoomSettingsRepository.kt` | Настройки и «открытая заметка» |
| **NoteViewModel** | `app/.../ui/editor/NoteViewModel.kt` | Состояние экрана ввода |
| Storage | `app/.../data/db/*` | Room/SQLite: таблицы `notes`, `settings` |
| UI | `app/.../ui/editor`, `ui/notes`, `ui/settings` | Экран ввода, список, настройки |

Зависимости направлены строго внутрь: `app → core`, `core →` только `kotlinx-coroutines`.

## 2. Поток данных при вводе

```
 палец(ы)                                   основной поток, без ожидания БД
    │  MotionEvent (DOWN / POINTER_DOWN / POINTER_UP / UP / CANCEL)
    ▼
 ChordPad (Compose pointerInput) ──► InputEngine ──► Chord(mask)
                                                     │
                                                     ▼
                       NoteViewModel.onChord ──► TypingSession ──► ChordSequenceDecoder ──► ChordCodec
                                │                     │
                                │                     ▼
                                │                TextEditor (текст, авторегистр, undo)
                                ▼
            snapshot-state (text, revision) ──► NoteTextArea перерисовывается в следующем кадре
                                │
                                └──► NoteAutosaver.onTextChanged ──(400 мс тишины, фон)──► Room
```

Обработчик касаний ничего не пишет в базу: он вызывает чистые функции в памяти, а запись
выполняет `NoteAutosaver` в фоновом скоупе приложения.

## 3. Механика аккорда (InputEngine)

* Каждое касание привязывается к клавише, на которую опустилось (K1…K5 — равные пятые доли
  ширины панели). Сдвиг пальца не меняет привязку; касание вне панели панель не получает вовсе.
* Цикл аккорда: от первого опущенного пальца до момента, когда отпущен последний.
* **Итоговая маска — объединение всех клавиш, нажатых за цикл** — так, как описывает алгоритм
  п. 5.2: маска обновляется при каждом новом касании, а фиксируется, когда отпущены все клавиши.
  Поэтому не важны ни порядок постановки пальцев, ни порядок отпускания, ни паузы между ними
  (п. 5.3 запрещает их учитывать). Длительность сохраняется только для диагностики.
  Следствие: если отпустить часть пальцев и, не отпуская остальные, поставить новый, он войдёт
  в тот же аккорд — новый аккорд начинается только после того, как отпущены все клавиши.
* Идемпотентность: повторный DOWN активного указателя и UP неизвестного указателя
  игнорируются; фиксация происходит только при переходе «есть пальцы → нет пальцев»,
  поэтому цикл даёт не более одного символа.
* Переиспользование id указателя системой внутри одного цикла учтено: вклад клавиш хранится
  счётчиками, а не таблицей `id → клавиша`.
* Отмена:
  * `ACTION_CANCEL` (жест системы, шторка, системный диалог) — Compose присылает его как
    «отпускание», уже помеченное consumed (проверено по исходнику Compose 1.7.6,
    `SuspendingPointerInputModifierNodeImpl.onCancelPointerInput`); аккорд сбрасывается без символа;
  * отмена одного указателя (`ACTION_POINTER_UP` + `FLAG_CANCELED`, Android 13+, например
    отбраковка ладони) — Compose её не различает, поэтому `MainActivity.dispatchTouchEvent`
    передаёт флаг через `TouchSignals`. По документации Android такое касание следует считать
    «не происходившим»: удаляется только этот палец, а остальные пальцы аккорда остаются
    законными и фиксируются как обычно (весь жест при этом системой не отменяется);
  * `ON_PAUSE`, потеря фокуса окна, уход панели из композиции — аккорд сбрасывается.
* Пальцы, которые оставались на экране во время отмены, «забываются» и не попадут в
  следующий аккорд.

## 4. Принцип кодировки

### 4.1 Представление

Комбинация — пятибитная маска `K1 K2 K3 K4 K5`, слева направо; `1` — клавиша участвовала в
аккорде. K1 — старший бит: `10000` = только K1, `00001` = только K5. `00000` символом не является.

### 4.2 Таблица v1.0 (п. 6.1 ТЗ)

| Символ | Код | Символ | Код | Символ | Код |
|---|---|---|---|---|---|
| О | 00100 | П | 01001 | Е | 00010 |
| У | 10001 | А | 01000 | Я | 11100 |
| И | 00001 | Ы | 01110 | Н | 10000 |
| Ь | 00111 | Т | 01100 | Г | 11010 |
| С | 00110 | З | 10110 | Р | 11000 |
| Б | 01101 | В | 00011 | Ч | 01011 |
| Л | 10100 | Й | 11001 | К | 01010 |
| Х | 10101 | М | 00101 | Ж | 10011 |
| Д | 10010 | Ш | 11110 | Ю | 01111 |
| Ц | 10111 | Щ | 11011 | Э | 11101 |

30 букв + префикс `11111` = все 31 ненулевая комбинация пяти бит. Ё не используется.

### 4.3 Расширенные символы

`11111` — служебный префикс: текстом не отображается, приложение ждёт второй аккорд.

| Последовательность | Результат |
|---|---|
| `11111 → 01000` | Ф |
| `11111 → 10000` | Ъ |

Пока префикс ожидает, клавиши панели получают акцентную рамку, а на K2 и K1 появляются
подсказки «Ф» и «Ъ» (вычисляются из таблицы, а не зашиты в UI).

Правила (`TypingSession`):

| Что нажато при ожидающем префиксе | Результат |
|---|---|
| `01000` / `10000` | Ф / Ъ |
| любой другой аккорд (включая повторный `11111`) | префикс отменён, символа нет |
| пробел, запятая, точка | префикс отменён **и** клавиша срабатывает (п. 6.2) |
| ⌫ или ↶ | отменяется только префикс — это последнее, что ввёл пользователь |
| уход приложения в фон | префикс молча сбрасывается |

Каждая отмена префикса сопровождается надписью «Префикс отменён» и тактильным сигналом
`REJECT` (если вибрация включена).

### 4.4 Где хранится таблица и как её менять

* `ChordTableV1.kt` — только данные в виде строк кодов из ТЗ, без логики.
* `ChordTable.from()` пропускает определение через `ChordTableValidator` (уникальность кодов
  и символов, 5 бит, нет `00000`, префикс не занят буквой, нет Ё, только заглавные буквы)
  и падает с понятной ошибкой, если таблица некорректна.
* `ChordTables` — реестр версий; версия хранится в настройках (`Settings.codeTableVersion`).
* Новая версия таблицы = новый файл-определение + строка в реестре. Движок ввода, декодер,
  редактор и UI при этом не меняются. Тест `shipped tables are all valid` проверяет все
  зарегистрированные таблицы.

## 5. Текст

* Курсор всегда в конце (ввод только дописыванием, удаление — последнего символа).
* Авторегистр не хранится флагом, а **выводится из текста**: буква заглавная, если перед ней
  только пробелы (начало заметки) или ближайший непробельный символ — точка. Поэтому после
  любого удаления, отмены или загрузки из БД правило автоматически верно.
* Удаление работает по символам, а не по аккордам: Ф/Ъ удаляются целиком, пробел и знаки — наравне с буквами.
* Отмена (↶) хранит обратные операции, а не снимки текста — O(1) памяти на шаг, лимит 500 шагов.

## 6. Сохранение и восстановление

* `NoteAutosaver`: запись через 400 мс после последнего изменения, но **не позже 2 с** после
  первого несохранённого изменения — даже при непрерывном быстром наборе без пауз краш теряет не
  больше ~2 с текста. Записи сериализованы (`Mutex`), всегда пишется самый свежий текст;
  начатая запись не прерывается.
* Ошибка записи: текст остаётся в памяти, статус «Ошибка сохранения», повтор с экспоненциальной
  паузой (1 → 30 с) — в том числе после выхода из редактора. Заметка удаляется как пустая только
  если пустым известно её *сохранённое* содержимое; если последний текст записать не удалось,
  заметка не удаляется.
* Новая заметка создаётся в БД только при первом непустом тексте; заметка, оставленная
  пустой, удаляется при выходе из редактора.
* Немедленная запись: при `ON_PAUSE`/`ON_STOP`, выходе из редактора, `onCleared`.
* Выход из редактора идемпотентен: повторное «Готово»/«Назад» до смены экрана ничего не делает.
* `WriteBarrier`: следующий экран, открывающий ту же заметку, дожидается финальной записи предыдущего.
* Room/SQLite в режиме WAL: после краша или принудительной остановки сохраняется всё, что
  было закоммичено последней транзакцией.
* Открытая в редакторе заметка запоминается (`settings.open_note_id`); при следующем холодном
  запуске приложение открывает её сразу. «Готово»/«Назад» очищают этот признак.
* Поворот: активность объявляет `configChanges`, поэтому не пересоздаётся; состояние в
  ViewModel, id заметки — в `SavedStateHandle` (переживает и смерть процесса). Если процесс
  погиб в первые сотни миллисекунд новой заметки, когда её id ещё не попал в сохранённое
  состояние, редактор находит её через `open_note_id` и не показывает пустую заметку.
* Признак «открытая заметка» пишет один владелец: после `close()` устаревшая запись его не перезапишет.
  Ошибка этой вспомогательной записи (например, переполненный диск) логируется и не роняет
  приложение; фоновые задачи приложения тоже не могут его уронить (`CoroutineExceptionHandler`).

## 7. Производительность на горячем пути

* Обработка касания и фиксация символа — синхронно на основном потоке, без аллокаций в
  движке (фиксированные массивы) и с O(1)-декодированием (массив на 32 элемента).
* Подсветка нажатых клавиш (и аккордных, и спецклавиш) читает состояние только в фазе
  отрисовки (`drawBehind`, `ColorProducer`) — нажатие перерисовывает клавишу без рекомпозиции.
  Подсказка аккорда вынесена в отдельный composable — пальцы рекомпозируют одну строку.
* Текст передаётся в текстовую область лямбдой: новый символ рекомпозирует только её, а не весь экран.
* Текстовая область раскладывает только хвост заметки (до 3000 символов) — стоимость кадра не
  растёт с длиной заметки. Прокрутка якорится к концу без дополнительного кадра (`reverseScrolling`).
* Анимации переходов отключены; БД — только из корутин Room на её исполнителях.

## 8. Принятые решения по неоднозначностям ТЗ

| Место ТЗ | Решение |
|---|---|
| «Список заметок либо последняя незавершённая» | Обычно — список; если приложение было закрыто, пока заметка была открыта, — сразу эта заметка |
| Неизвестный второй аккорд после префикса | Префикс отменяется без символа (ни один аккорд не даёт «неожиданного» символа) |
| ⌫/↶ при ожидающем префиксе | Отменяют только префикс |
| Таймаут префикса | Нет: префикс ждёт следующего действия, его состояние всегда видно |
| Спецклавиши | Пробел/запятая/точка срабатывают на отпускании внутри клавиши; ⌫ — на нажатии с автоповтором при удержании |
| Палец сместился на другую клавишу | Остаётся привязан к исходной клавише |
| Вырез камеры | Текст обходит вырез, клавиши занимают всю ширину |
| Системный жест «Назад» | Исключён над аккордной панелью (`systemGestureExclusion`; система выделяет ≈200 dp на край, их отдаём панели) |
| Отмена ОС одного пальца | Удаляется только этот палец, остальные пальцы аккорда фиксируются (см. п. 3) |
| Поиск | Регистронезависимый по содержимому в Kotlin (SQLite `LIKE` не сворачивает регистр кириллицы) |
| Тема | Тёмная по умолчанию, светлая — в настройках (п. 4.3 разрешает) |
