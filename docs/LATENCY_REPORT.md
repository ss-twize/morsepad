# MorsePad — отчёт об измерении задержек

Версия приложения: 1.0 · Дата измерений: 2026-10-11

> **Статус.** Ниже — измерения на эмуляторе. По ТЗ (п. 10) окончательная проверка выполняется
> на реальном устройстве; эмулятор не воспроизводит тачскрин, частоту опроса сенсора и
> графический конвейер телефона. Раздел 5 — порядок замера на устройстве и таблица для его
> результатов: инструментирование уже встроено в приложение, замер не требует правок кода.

## 1. Что и как измеряется

Все отметки времени берутся из одних монотонных часов (`CLOCK_MONOTONIC`): время события
`MotionEvent` (его присваивает система ввода), `System.nanoTime()`, `Choreographer`, `FrameMetrics`.

| Метрика (имя в CSV) | От | До |
|---|---|---|
| `chord_release_to_text_draw_ms` | отпускание **последнего** пальца аккорда (время `MotionEvent`) | отрисовка нового текста в UI-потоке |
| `chord_release_to_frame_ready_ms` | то же | кадр с новым символом готов и передан системному компоновщику (HWUI `FrameMetrics`: intended vsync + total duration). На экране он появляется на ближайшем vsync — не позже чем через один период обновления (16,7 мс при 60 Гц, 8,3 мс при 120 Гц) |
| `special_key_to_text_draw_ms` | отпускание пробела/запятой/точки (нажатие для ⌫) | отрисовка текста |
| `input_event_to_text_change_ms` | событие касания | текст изменён в памяти приложения (доставка события + обработка) |

Сопоставление «событие → кадр» идёт по ревизии текста и vsync-метке кадра
(`app/.../diagnostics/LatencyTracker.kt`). Если несколько аккордов попали в один кадр,
измеряется последний — поэтому `n` чуть меньше числа символов. Статистика:
скользящее окно 4096 сэмплов, перцентили методом ближайшего ранга (`core/.../diagnostics/LatencyStats.kt`).

## 2. Как получены данные

Тест `InputPipelineLatencyTest` открывает новую заметку в настоящем приложении и подаёт
аккорды через **системный конвейер ввода** (`UiAutomation.injectInputEvent` → InputDispatcher →
окно) настоящими многоточечными `MotionEvent`: пальцы ставятся с интервалом 4 мс, держатся
16 мс и отпускаются по очереди. Аккорды — случайные из всех 31 комбинаций (фиксированный seed).

* **steady** — 240 аккордов с паузой 80 мс (≈ 6 аккордов/с, темп уверенного набора);
* **burst** — 300 аккордов без пауз (≈ 13 аккордов/с — предел скорости инъекции на эмуляторе).

Каждый прогон дополнительно проверяет, что итоговый текст **в точности** совпадает с ожидаемым
(эталон вычисляется тем же ядром на JVM-стороне), т.е. ни один символ не потерян и не задвоен.

### 4.1 Основной стенд: benchmark-сборка, аппаратный GPU хоста

| Режим | Метрика | n | mean | p50 | p90 | p95 | p99 | max |
|---|---|---|---|---|---|---|---|---|
| steady | отпускание → отрисовка текста | 218 | 11,8 | 11,9 | 18,7 | 19,9 | 22,0 | 22,9 |
| steady | **отпускание → кадр готов** | 217 | 26,3 | 26,5 | 33,0 | 34,1 | **35,5** | 37,3 |
| steady | событие → текст изменён | 218 | 1,7 | 1,6 | 2,4 | 2,6 | 4,0 | 7,1 |

Значения в миллисекундах. Потерянных и лишних символов: **0 из 540**.
Сырые сэмплы: [`docs/latency-data/`](latency-data/) (CSV, формат `metric,index,value_ms`, сводка в заголовке).

### 4.2 Сравнение конфигураций (отпускание → кадр готов, steady, мс)

| Конфигурация | p50 | p95 | p99 |
|---|---|---|---|
| benchmark + аппаратный GPU (итоговая сборка) | 26,5 | 34,1 | 35,5 |
| benchmark + аппаратный GPU (до оптимизаций по итогам ревью) | 27,9 | 35,4 | 37,1 |
| debug + аппаратный GPU (до оптимизаций) | 27,0 | 34,3 | 41,5 |
| debug + программный GPU swiftshader (до оптимизаций) | 49,4 | 80,6 | 96,7 |

Программная растеризация 2400×1080 на CPU хоста добавляет 20–60 мс на стадии GPU — это
артефакт стенда, а не приложения: UI-поток в той же конфигурации укладывается в
p50 ≈ 18 мс до отрисовки.

### 4.3 Выводы

* Обработка в приложении (декодирование аккорда, редактор, публикация состояния) занимает
  единицы миллисекунд: p99 ≈ 4–5 мс от события до изменения текста.
* Основная часть задержки — ожидание следующего vsync (в среднем половина периода) и работа
  графического конвейера; приложение не ждёт базу данных и не блокирует поток.
* На эмуляторе с аппаратным GPU цель ТЗ «до 50 мс» выполняется для p99 «отпускание → кадр
  готов» (35,5–37,7 мс). С учётом ожидания вывода на экран (+ ≤ 16,7 мс при 60 Гц) медиана
  появления символа ≈ 35 мс. Единственный выброс 68 мс в режиме burst совпал с выбросом
  доставки события (33 мс) — пауза эмулятора/хоста, а не работа приложения; на устройстве
  хвост распределения нужно подтвердить по p99/max реального замера.
* Длинные заметки не увеличивают стоимость кадра: на экране ввода раскладывается не более
  3000 последних символов.

## 5. Замер на реальном устройстве

### 5.1 Автоматический (рекомендуется)

1. Включить на телефоне режим разработчика и отладку по USB, подключить кабель.
2. Выполнить:
   ```bash
   ./gradlew :app:connectedBenchmarkAndroidTest -PtestBuildType=benchmark -Pandroid.testInstrumentationRunnerArguments.class=com.morsepad.app.InputPipelineLatencyTest
   ```
   Чтобы CSV не удалились вместе с приложением после прогона, добавьте
   `-Pandroid.injected.androidTest.leaveApksInstalledAfterRun=true`.
3. Результаты — в `adb logcat -s MorsePadLatency` и в CSV:
   ```bash
   adb pull /sdcard/Android/data/com.morsepad/files/
   ```

Инъекция обходит физический тачскрин, поэтому этот замер не включает задержку сенсора и
драйвера — она одинакова для любого приложения.

### 5.2 Ручной, с реальными пальцами

1. Установить `dist/MorsePad-1.0-release.apk`.
2. «Настройки → Диагностика задержек → Сбросить».
3. Набрать 3–5 минут обычного текста (быстрые аккорды, частые переключения клавиш,
   заметка длиннее 2000 символов).
4. «Обновить» — сводка на экране; «Сохранить CSV» — файл с сэмплами:
   ```bash
   adb pull /sdcard/Android/data/com.morsepad/files/
   ```

Метка времени события здесь — время, присвоенное ядром/драйвером тачскрина, поэтому метрика
охватывает весь путь от отпускания пальца до готового кадра.
